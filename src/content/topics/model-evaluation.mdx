## Mental model

<Analogy title="A flight simulator, not a school exam">

A useful validation set is a simulator of the decisions the deployed model will face. A random split can be a perfect school exam yet a terrible simulator if the same user, device, hospital, merchant, or future-derived feature appears on both sides. The evaluation protocol is part of the model.

</Analogy>

## Metric families

### Classification

| Question | Useful measures | Common trap |
| --- | --- | --- |
| Can the model rank positives above negatives? | ROC-AUC, PR-AUC | ROC-AUC can look strong under extreme imbalance |
| Are positive predictions trustworthy? | precision, PPV | depends on prevalence and threshold |
| Are costly positives being missed? | recall, sensitivity | high recall can flood reviewers |
| Are probabilities meaningful? | log loss, Brier score, calibration curve | accuracy cannot diagnose probability quality |
| Does one operating point meet constraints? | confusion matrix, cost, recall at fixed precision | choosing threshold on the test set |

`Fβ` weights recall `β²` times as strongly as precision. It is useful only when that weighting reflects the decision, not because one score is convenient.

### Regression and forecasting

- **MAE:** linear penalty, interpretable in target units, more robust to outliers.
- **RMSE:** emphasizes large errors; appropriate when large misses are disproportionately expensive.
- **Quantile loss:** evaluates conditional quantiles and asymmetric costs.
- **MAPE:** unstable near zero and misleading with signed or small denominators.
- **Prediction-interval coverage and width:** required when uncertainty affects decisions.

<KeyIdea><p>A metric compresses a distribution of errors. Always inspect the distribution, slices, and examples that the scalar hides.</p></KeyIdea>

## Validation protocols

1. **Random stratified split:** appropriate when rows are exchangeable and class balance matters.
2. **Group split:** keeps all records for one entity in a single fold.
3. **Temporal split:** trains on the past and evaluates on a later period.
4. **Rolling/expanding windows:** measures stability across multiple future-like periods.
5. **Nested cross-validation:** separates hyperparameter selection from unbiased performance estimation when data is limited.

### Leakage checklist

- Was any feature computed using information available only after prediction time?
- Were scalers, encoders, imputers, vocabulary, or feature selection fit before splitting?
- Can duplicate or near-duplicate entities cross the boundary?
- Does a label proxy directly encode the outcome?
- Did threshold or hyperparameter decisions use the final test set?

## Thresholds, calibration, and cost

Suppose false negatives cost `C_FN`, false positives cost `C_FP`, and a threshold produces counts `FN(t)` and `FP(t)`. A simple operating objective is:

`expected_cost(t) = C_FN·FN(t) + C_FP·FP(t)`

Real systems add review capacity, customer friction, delayed recovery, and legal constraints. Choose the threshold on validation data, freeze it, and report the untouched test result.

Calibration asks whether predictions near 0.7 are positive about 70% of the time. A model can rank well but calibrate poorly. Temperature scaling, isotonic regression, or Platt-style calibration must be fit on data not used to train the base model.

<Pitfalls>

- Reporting accuracy for rare-event detection.
- Balancing the test set and then presenting precision as if it reflects production prevalence.
- Resampling before the train/validation split.
- Performing feature selection on the entire dataset.
- Optimizing hundreds of experiments against one “untouched” test set until it is no longer untouched.
- Ignoring confidence intervals when test cohorts are small.
- Declaring a model better from a tiny aggregate gain that reverses on critical slices.

</Pitfalls>

### Choose in this order

1. Define the decision and the cost of each error.
2. Choose a future-like, leakage-safe split.
3. Select a metric family for ranking, probability quality, or point prediction.
4. Choose calibration and threshold policy on validation data.
5. Report slices, uncertainty, capacity constraints, and drift monitoring.

### Fast warnings

- rare positives → inspect precision, recall, PR-AUC, and operating cost; do not lead with accuracy
- repeated entities → use a group split
- time changes the problem → use temporal or rolling validation
- probabilities drive decisions → test calibration
- repeated model selection → keep a genuinely untouched final test set

## Interview case

<InterviewPrompt title="Fraud threshold" difficulty="Medium" timebox="12 min">

A fraud model sees 0.2% positives. False negatives cost ₹8,000 on average and false positives cost ₹35 in review time. Propose an evaluation and threshold-selection plan.

<Hint>Accuracy is not decision-aware. Turn the cost asymmetry into an expected-value calculation and protect the time boundary.</Hint>

<Solution>

Use temporal and entity-aware splits, keeping all events for an account or instrument together. Report PR-AUC, recall at review-capacity constraints, precision, calibration, and expected cost. Choose a threshold on validation data, evaluate once on a later untouched window, and slice by channel, merchant/customer cohort, geography, and amount. Monitor base-rate, feature, calibration, and decision drift after deployment. Include uncertainty and delayed-label handling.

**Rubric:** leakage-safe split; imbalance-aware metrics; threshold tied to cost/capacity; calibration; slice and drift plan.

</Solution>
